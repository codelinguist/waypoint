`DRAFT`

- Priority: First usable frontend slice (Phase 9 early slice, D015)

  - `assets[]`: `id, name, assetType, estimatedValue, planningValue, currency, valuedAt, liquidity, sourceType`
  - `liabilities[]`: `id, name, liabilityType, outstandingBalance, currency, balanceAsOf, sourceType`
  - `totalsByCurrency[]`: `currency, assetTotal, liabilityTotal, netWorth` — one entry per currency present in either list, ordered by currency; `netWorth = assetTotal - liabilityTotal`; all monetary fields are exact decimal strings, never JavaScript `Number`

## Information and actions

- Information the user must understand: household name; net worth, assets total and liabilities total per currency (currencies never combined); for each record — name, type, currency, source date, liquidity (assets) or nothing implying liquidity (liabilities), and whether it came from manual entry or import; that `planningValue` (used in every total) can differ from `estimatedValue`, and why (conservative treatment of illiquid/uncertain holdings, principle 9); that `retrievedAt` is when the page fetched data, not a valuation date for every row (rows carry their own `valuedAt`/`balanceAsOf`)
- Primary action: understand current position (headline totals) by currency
- Secondary actions: inspect the source rows behind a total; refresh
- Financial classifications that must remain explicit: planning value vs. estimated value (never silently substituted, principle 3/9); liquidity (must not imply all wealth is spendable cash, per the parent brief); asset vs. liability (never merged into one undifferentiated "record"); per-record source date vs. page retrieval time; manual-entry vs. imported provenance

## Directions explored

### Direction A — Currency-first summary cards, expandable holdings

- Structure: one card per currency, each headlined by a visibly labeled "Net worth" figure (assets total / liabilities total shown beneath), with an expand/collapse control that reveals two source-row tables (assets, liabilities) inside the card. Progressive disclosure: the collapsed headline is the actual default; records are one action away. Below 700px, an expanded record renders as a stacked card (name as title, other fields as labeled rows) instead of a horizontal table row — see R1 below.
- Interaction: a labeled toggle button (`aria-expanded`/`aria-controls`) per card shows/hides its records; each record region is also a keyboard-focusable, `aria-label`led scroll container at widths where it would otherwise need horizontal scrolling.
- Strengths: directly matches the parent brief's stated flow ("sees recorded totals grouped by currency" first, "inspects what contributes to each total" second); each total sits immediately beside the rows that produce it, so reconciliation needs no cross-referencing; degrades cleanly to narrow width (cards already stack; collapsed-by-default cards keep the initial screen short on mobile); a household with many currencies scales by adding cards, not by widening anything.
- Tradeoffs: a household that wants to see every record at once must expand every card; on first load, only headline totals are visible without the extra click/tap.

### Direction B — Inventory-first split view

- Structure: two persistent columns, Assets and Liabilities, each internally grouped by currency; every record is always visible as a compact list row. A single summary bar of per-currency net-worth "chips" sits above the columns.
- Interaction: no expand/collapse — everything is always rendered; the chip row scrolls horizontally if it doesn't fit.
- Strengths: nothing is ever hidden behind an interaction; a household that wants to audit every record at a glance can, without clicking anything.
- Tradeoffs: totals live only in the chip row, disconnected from the rows that produce them — matching a chip back to "why is this number what it is" means scanning two separate, currency-grouped lists rather than reading one adjacent block; below ~720px the two columns must stack (Assets, then Liabilities), turning the page into two long lists with the chip summary now far above the liabilities the user is currently scrolled past; weakest fit for the parent brief's "totals first, sources second" flow, since sources are already fully unfolded.

### Direction C — Unified reconciling ledger

- Structure: a single dense table containing every asset and liability row together, grouped by currency with a subtotal (net-worth) row closing each currency group; a `Kind` column (Asset/Liability, icon + label, not color alone) distinguishes row types; toolbar filters for currency and kind.
- Interaction: filter selects narrow the visible rows; the whole table sits in one horizontally-scrollable container.
- Strengths: most information-dense single view; appeals to a systems-thinking, spreadsheet-comfortable user (matches Ralph's stated preference in `docs/product/user-zero.md`); filtering is a natural fit for a household with many records.
- Tradeoffs: the headline "what's my net worth right now" answer is buried inside the table (a subtotal row reached only after scanning past every row in that currency group) rather than presented immediately; weakest narrow-width story of the three — a genuinely tabular structure with six columns has no good stacked-card fallback without abandoning the structure the direction is built around, so it stays a horizontally-scrolling table even at 390px, which is more friction than Directions A or B for the mobile-first ordinary case.

**Product Owner's revision-1 direction decision:** retain Direction A for revision (2026-09-10 review, WAP-13 comment). B and C remain as materially distinct comparison evidence, unchanged this revision. This is a preferred direction for continued revision, not yet `APPROVED` design.

## Proposed direction

- Recommendation: **Direction A — currency-first summary cards, expandable holdings.**
- Reasoning: it is the only direction whose default (unexpanded) view already matches the parent brief's stated two-step flow — see totals by currency, then inspect sources — without requiring the user to scan across a disconnected summary bar (Direction B) or hunt through a dense table for the subtotal row (Direction C). It also has the cleanest narrow-width behavior of the three: cards were already a stacking layout before any responsive work is added, and starting each card collapsed keeps the first mobile screen to four short headlines instead of six-plus columns of detail. Direction C's density is real but optimizes for a power-user audit action this task's parent brief does not ask for (browsing/filtering every record at once); that is better served as a later, explicit power view than as the default first screen.
- Collapsed default (the actual first-load state): `evidence/direction-a-currency-cards/populated-collapsed.html`, `screenshots/direction-a-populated-collapsed-{wide,narrow}.png`. All four currency cards collapsed; each headline is visibly labeled "Net worth" (not screen-reader-only), and a short always-visible explainer line states net worth precisely ("recorded asset planning values minus outstanding liability balances") and that retrieval time does not change a record's own date.
- Expanded records (record-inspection evidence): `evidence/direction-a-currency-cards/populated-expanded.html`, `screenshots/direction-a-populated-expanded-{wide,narrow}.png`. Same four currencies; PHP (ordinary mixed currency) and EUR (liabilities-only — explicit empty asset side) start expanded to show record inspection for both cases side by side; USD and JPY (assets-only) stay collapsed for contrast.
- Narrow layout (390px): each expanded record renders as a stacked card — full-width record name as the title, then labeled key/value rows for type, liquidity, values, dates and source — instead of a horizontal table row. This replaces the letter-by-letter name wrapping the first revision had (R1 below) with normally word-wrapped text at full width, and needs no horizontal scrolling at all in this evidence's widths.
- Loading state: `evidence/direction-a-currency-cards/loading.html` / `screenshots/direction-a-loading-wide.png`. Four skeleton cards (matching the four-currency dataset), `aria-hidden`; the status line reads "Loading financial position…" via `role="status" aria-live="polite"`. No number, zero or blank total is ever rendered before real data arrives.
- Empty state: `evidence/direction-a-currency-cards/empty.html` / `screenshots/direction-a-empty-wide.png`. A valid, reachable household with zero recorded rows gets a plain "no assets or liabilities are recorded yet" message and an instruction to add records elsewhere — never a fabricated zero-currency group and never treated as an error.
- First-load failure (no prior data): `evidence/direction-a-currency-cards/error-first-load.html` / `screenshots/direction-a-error-first-load-wide.png`. Distinct from refresh failure below: there is no prior successful result to retain, so the page shows only a failure message and a retry action — no card, no currency, no zero total is fabricated to fill the space.
- Refresh failure (prior data retained): `evidence/direction-a-currency-cards/error-refresh-failed.html` / `screenshots/direction-a-error-refresh-failed-{wide,narrow}.png` demonstrates the **refresh-failure retention decision** this design makes explicitly: a failed refresh keeps the same complete prior response — all four currencies, unchanged totals, records still fully inspectable via working expand/collapse (PHP shown expanded) — dimmed, with a `role="alert"` banner naming the failure time, rather than clearing the screen, stripping record controls, or silently mixing old rows with a partial new response.
- Missing configuration: `evidence/direction-a-currency-cards/configuration-missing.html` / `screenshots/direction-a-configuration-missing-wide.png`. No `HOUSEHOLD_ID` configured at all; shown before any household name is known (no card layout, no household-scoped heading).
- Configured household not found: `evidence/direction-a-currency-cards/configuration-not-found.html` / `screenshots/direction-a-configuration-not-found-wide.png`. A distinct message from the missing-configuration case — names the specific configured ID that returned 404, since the fix differs (correct the ID vs. set one at all).
- Keyboard-focus evidence: `screenshots/direction-a-keyboard-focus-{wide,narrow}.png` — real `Tab`-key navigation (not a simulated `:focus` state) from page load to the first record-toggle button, showing the visible focus ring.
- 200%-zoom reflow evidence (simulation, not a literal browser-zoom capture — see R2 below): `screenshots/direction-a-reflow-200pct-640.png`, a real 640px viewport against `populated-expanded.html` with every currency's records expanded, including JPY's extreme-precision row. Per the WCAG 1.4.10 reflow-testing convention, a browser at 200% zoom gives a page a CSS layout viewport roughly half its unzoomed width, so testing "a 1280px window at 200% zoom" is done by testing a 640px viewport directly. Confirmed zero horizontal overflow (`document.documentElement.scrollWidth === clientWidth === 640`) and correct reflow into the stacked record layout, including the extreme JPY amount, at that width.
- Accessibility considerations: every amount uses `font-variant-numeric: tabular-nums`; negative/positive net worth is marked with an explicit `−`/`+` glyph plus visible "NET WORTH" label text, not color or screen-reader-only text alone; expand/collapse uses real `<button>` elements with `aria-expanded`/`aria-controls`, keyboard-operable with no custom key handling needed; a horizontally-scrollable record region is a `role="region"` with `tabindex="0"` and its own `aria-label`, and gets a distinct visible focus ring so a keyboard user knows the region itself is focused before scrolling it; the status/refresh-failure line is an `aria-live` region so screen-reader users hear load/refresh outcomes without navigating to find them; visible focus rings (`:focus-visible`, 3px, not removed) on every interactive element; no fixed pixel width on any container that would break 200% browser zoom — verified as a reduced-layout-viewport reflow simulation (640px, see the 200%-zoom bullet above), not a literal OS/browser zoom capture; be explicit about that distinction when citing this evidence, since claiming literal browser zoom without capturing it is itself a defect (R2 below). A large exact-decimal net-worth headline (e.g. the JPY case) is a single long token with no internal spaces — it needs `overflow-wrap: anywhere` so it wraps within itself at narrow widths instead of forcing page-level horizontal scroll; verify with `document.documentElement.scrollWidth` against the viewport width, not just a visual screenshot check, since a downscaled preview image can hide overflow pixels or a barely-readable-but-technically-non-overflowing layout (R1 below).

## Revision 1 (resolves independent review VR-001 through VR-004)

Codex's independent review of PR #35 (revision `9718f80`) returned `RETURNED` with three `BLOCKING` findings and one `RECOMMENDED` finding, retaining Direction A for revision. Full findings are recorded on the WAP-13 Jira issue (2026-09-10). Resolution:

- **VR-001 (BLOCKING — mobile records unreadable).** At 390px, the original single horizontally-scrolling table squeezed the name column so narrow that names broke letter-by-letter ("Prima / ry / Chec / king / Acco / unt"); passing a page-level `scrollWidth` check didn't establish the *records* were usable, only that the *page* wasn't overflowing. Fixed by replacing the narrow-width table with a stacked-card record layout (`table.stackable` in `evidence/shared.css`, applied below 700px): each record becomes its own bordered block with the name as a full-width title and other fields as labeled rows, so names wrap normally instead of being squeezed into a fixed column. Added `tabindex="0"` + `role="region"` + `aria-label` to every record scroll container (for widths where horizontal scrolling could still occur) with its own visible focus ring. New evidence: `populated-expanded.html` narrow screenshots (readable stacked records), `direction-a-keyboard-focus-*.png` (real Tab-key focus). The first attempt at 200%-zoom evidence was itself found incorrect on re-review — see R2 below.
- **VR-002 (BLOCKING — headline meaning hidden).** "Net worth" was previously only in `.sr-only` text, and the planning-value/retrieval-time explanation only existed inside expanded records (invisible by default). Fixed: every card now has a visible "NET WORTH" label above the figure, and a short always-visible explainer line sits under the status line on every populated state, visible without expanding anything. Added the true collapsed-default state as its own file (`populated-collapsed.html`) with wide and narrow evidence, separate from the expanded-record evidence (`populated-expanded.html`), so both are now independently reviewable. This revision's explainer wording was itself found imprecise on re-review (it read as if liabilities also carry a "planning value") — see R2 below.
- **VR-003 (BLOCKING — failure/one-sided states unspecified).** Three gaps, all fixed: (1) added `error-first-load.html` for an initial network/server failure with no prior data — retry action, no fabricated card or total, distinct from the retained-stale-data case; (2) added a fourth synthetic currency, EUR, that is liabilities-only (zero asset total, explicit "No assets recorded in EUR" line, negative net worth), covering the liabilities-only case the dataset previously lacked (it only had the assets-only JPY case); (3) rebuilt the refresh-failure evidence (`error-refresh-failed.html`, renamed from `error.html`) to show the *same complete* four-currency response as the populated states with working expand/collapse (previously it silently dropped the JPY group and had no record controls at all); (4) split the configuration state into two distinct files/messages — `configuration-missing.html` (nothing configured) and `configuration-not-found.html` (a specific configured ID returned 404, named in the message) — rather than one generic message covering both.
- **VR-004 (RECOMMENDED — process assurances in household copy).** Removed engineering-assurance phrasing from on-screen text (e.g. "this view never estimates or fabricates a starting balance", "this page never invents household data") from `empty.html` and `configuration-missing.html`; that reasoning now lives only in this brief and its evidence-note footers, not in copy a household would read. Also: the stale PR reference to the retired `implementation-log.md` no longer applies — that file (root and feature-local alike) was removed from the repository entirely in a separate, unrelated change; the PR description here has been corrected to stop citing it.

## Revision 2 (resolves re-review VR-001/VR-002 evidence gaps)

Codex's independent re-review of PR #35 (revision `7b7dc28`) returned `RETURNED` again (2026-09-11), finding VR-003 and VR-004 fully resolved but VR-001 and VR-002 only partly resolved — the design fixes themselves were sound, but two pieces of evidence were wrong or incomplete:

- **VR-001 (PARTLY RESOLVED → resolved — wrong zoom-evidence technique).** Revision 1's `direction-a-zoom200-wide.png` used Chromium's non-standard `zoom` CSS property at a 1280px viewport, claiming it demonstrated 200%-zoom reflow. On re-review this was caught as incorrect: `zoom` visually scales rendering without changing the CSS layout viewport that media queries evaluate against, so it never actually exercised the 700px stacked-layout breakpoint — the screenshot still showed the ordinary wide table. Fixed by removing that file and technique entirely and replacing it with `screenshots/direction-a-reflow-200pct-640.png`: a real 640px viewport (the WCAG 1.4.10 convention for testing "a 1280px window at 200% zoom," since browser zoom roughly halves the CSS layout viewport) against `populated-expanded.html` with **every** currency expanded, including JPY's extreme-precision row — so the fix is evidenced for both ordinary names and the hardest amount case together. Verified `scrollWidth === clientWidth === 640` (zero overflow) and correct reflow into the stacked-card layout. This is explicitly documented as a viewport-reduction *simulation* of 200% zoom, not a literal OS/browser zoom capture, per the review's own guidance on how to represent whichever technique is actually used.
- **VR-002 (PARTLY RESOLVED → resolved — refresh-failure state missing the explainer, and imprecise wording).** Two gaps: (1) `error-refresh-failed.html` never got the always-visible explainer line Revision 1 added everywhere else, contradicting the brief's own claim that it appeared on every populated/error state — fixed by adding the identical `.explainer` element to that file, screenshot refreshed; (2) the explainer's wording ("using each record's planning value") was imprecise — only assets have a `planningValue` field; liabilities use `outstandingBalance` — so as written it implied liabilities also carry a "planning value." Fixed by replacing the wording everywhere the explainer appears (`populated-collapsed.html`, `populated-expanded.html`, `error-refresh-failed.html`) with the review's suggested precise copy: "Net worth is recorded asset planning values minus outstanding liability balances. Records keep their own valuation or balance dates; refreshing does not update those dates." All three affected screenshots were regenerated.
